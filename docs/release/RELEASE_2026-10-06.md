# Release 2026-10-06: dev to main

Ships PR #108 (overnight QA fixes, ATOL listing rule) and PR #109 (account erasure, 90-day enquiry retention, truthful privacy page, full data export).

Production SQL is run by Ali in the Supabase SQL editor (production project). No agent runs it. Each block below was applied to the local stack (`pc-local-db`) in order, twice, with no error and no change on the second pass: see "Local proof" at the end.

## Order

1. **READ-ONLY CHECKS.** Record the results. Stop if query 4 is not 0 or a number you accept.
2. **PRE-DEPLOY.** Additive only.
3. Merge dev into main. Wait for the Vercel production deployment to be READY. Run the smoke tests.
4. **POST-DEPLOY.** Revokes.
5. Rerun READ-ONLY CHECKS. Query 1 must now be all PASS.

The SQL editor shows only the last result. Each block ends in a check query so the last result is the one that matters. To read an earlier query in the READ-ONLY block, highlight that one SELECT and press Run: a lone SELECT is its own transaction and cannot write.

## Which block each statement is in, and why

| Statement | Block | Evidence |
|---|---|---|
| `ALTER TABLE operator_profiles ADD COLUMN IF NOT EXISTS atol_verified_at / abta_verified_at` (013) | PRE-DEPLOY | Additive and nullable. No code on main or on dev reads or writes these columns: the Prisma model has `atol_number` and `abta_member_number` only (`prisma/schema.prisma:185-186`), and the adapter maps neither date (`lib/api/db/adapter.ts:51-66`). `atolVerifiedAt` exists only in the TypeScript type (`lib/types.ts:67`) and is never persisted. So deploying before or after the columns exist is safe both ways. The code change that reads them is a later release (013 header) and must ship after POST-DEPLOY. |
| `GRANT INSERT ON public.interests TO service_role` | PRE-DEPLOY | The Hajj "notify me" form inserts through the Supabase service role: `app/api/interest/route.ts:34-38`. That is true on main and on dev. The local stack's default privileges leave `service_role` with no INSERT on `interests` (PR109 report, risk 2), so production may be missing it too. GRANT is additive and idempotent. No SELECT grant is added: after this release no code reads `interests` through the API (export reads it through Prisma, `app/api/user/export/route.ts:20` → `lib/api/db/adapter.ts:706`; deletion likewise, `lib/api/db/adapter.ts:702`). Nothing on `interests` is revoked, so main keeps whatever it has until the new code is live. |
| `REVOKE ALL ON public.operator_profiles FROM anon, authenticated` (014) | POST-DEPLOY | A revoke, so it runs only after the new code is live. No code on main or dev reaches `operator_profiles` through the API roles: `git grep "from('operator_profiles')"` finds nothing on `origin/main`, `origin/dev` or the release head; every read and write is Prisma on the server. No storage or table policy reads `operator_profiles` from another table (only its own policies, `supabase/migrations/001_enable_rls.sql:33-37` and `009_update_policies_with_check.sql:40`), so no policy subquery breaks. Between PRE-DEPLOY and POST-DEPLOY the new 013 columns are writable by the API roles if query 1 shows FAIL, exactly like the existing verification columns. That window is harmless for the new columns because no code reads them yet. |
| Enquiry retention cron (`/api/cron/enquiry-retention`) | No SQL | Runs through Prisma on the server connection (`lib/api/db/adapter.ts:687`), which needs no API-role grant. Needs `CRON_SECRET` set in Vercel production. |

## READ-ONLY CHECKS

Run before PRE-DEPLOY and again after POST-DEPLOY. Ends in ROLLBACK and is read only: any write inside it would fail.

```sql
BEGIN TRANSACTION READ ONLY;

-- Query 1 (PRODUCTION_CHECKS.sql): can the API roles touch the verification fields?
-- Before POST-DEPLOY: FAIL rows are expected if Supabase default grants are present.
-- After POST-DEPLOY: every row must say PASS.
SELECT c.check_name,
       c.allowed,
       CASE WHEN c.allowed THEN 'FAIL' ELSE 'PASS' END AS result
FROM (
  SELECT format('%s can UPDATE operator_profiles.%s', r.role, col.name) AS check_name,
         has_column_privilege(r.role, 'public.operator_profiles', col.name, 'UPDATE') AS allowed
  FROM (VALUES ('authenticated'), ('anon')) AS r(role)
  CROSS JOIN (
    SELECT column_name::text AS name
    FROM information_schema.columns
    WHERE table_schema = 'public' AND table_name = 'operator_profiles'
      AND column_name IN ('verification_status', 'verified_at', 'tier', 'can_receive_bookings',
                          'payment_sla_flagged', 'onboarding_complete', 'bank_details_active',
                          'atol_number', 'abta_member_number', 'atol_verified_at', 'abta_verified_at', 'slug')
  ) AS col
  UNION ALL
  SELECT format('%s can %s operator_profiles', r.role, p.priv),
         has_table_privilege(r.role, 'public.operator_profiles', p.priv)
  FROM (VALUES ('authenticated'), ('anon')) AS r(role)
  CROSS JOIN (VALUES ('INSERT'), ('UPDATE'), ('DELETE'), ('SELECT'), ('TRUNCATE')) AS p(priv)
) AS c
ORDER BY result, c.check_name;

-- Query 2 (PRODUCTION_CHECKS.sql): row level security on every table. Expected: rls_enabled true everywhere.
SELECT n.nspname AS schema, c.relname AS table_name,
       c.relrowsecurity AS rls_enabled, c.relforcerowsecurity AS rls_forced,
       (SELECT count(*) FROM pg_policies p WHERE p.schemaname = n.nspname AND p.tablename = c.relname) AS policy_count,
       has_table_privilege('anon', c.oid, 'SELECT') AS anon_select,
       has_table_privilege('authenticated', c.oid, 'UPDATE') AS authenticated_update
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname IN ('public', 'storage') AND c.relkind IN ('r', 'p')
ORDER BY c.relrowsecurity, n.nspname, c.relname;

-- Query 3 (PRODUCTION_CHECKS.sql): every policy. Compare with supabase/migrations/001, 005, 006, 008, 009, 010, 011.
SELECT schemaname, tablename, policyname, permissive, roles, cmd,
       qual AS using_expression, with_check
FROM pg_policies
WHERE schemaname IN ('public', 'storage')
ORDER BY schemaname, tablename, policyname;

-- Query 4 (PRODUCTION_CHECKS.sql): verified operators the ATOL rule hides on release. Expected: 0 or an accepted number.
SELECT count(*) AS verified_without_atol
FROM public.operator_profiles
WHERE verification_status = 'verified'
  AND (atol_number IS NULL OR btrim(atol_number) = '');

-- Query 5: enquiries the first retention run will anonymise (cannot be undone).
SELECT count(*) AS enquiries_to_anonymise_on_first_run
FROM public.enquiries
WHERE created_at < now() - interval '90 days'
  AND (email IS NOT NULL OR phone IS NOT NULL OR message IS NOT NULL
       OR name NOT IN ('Deleted account', 'Removed after 90 days'));

-- Query 6: grants on interests. After PRE-DEPLOY service_role must show INSERT.
SELECT r.role,
       has_table_privilege(r.role, 'public.interests', 'INSERT') AS can_insert,
       has_table_privilege(r.role, 'public.interests', 'SELECT') AS can_select,
       has_table_privilege(r.role, 'public.interests', 'DELETE') AS can_delete
FROM (VALUES ('service_role'), ('authenticated'), ('anon')) AS r(role)
ORDER BY r.role;

ROLLBACK;
```

## PRE-DEPLOY

Additive only. Safe to run twice. Run before merging dev into main.

```sql
BEGIN;

-- 013: when an admin checked ATOL / ABTA. Nullable, no backfill, unused by this release's code.
ALTER TABLE public.operator_profiles ADD COLUMN IF NOT EXISTS atol_verified_at timestamptz;
ALTER TABLE public.operator_profiles ADD COLUMN IF NOT EXISTS abta_verified_at timestamptz;

-- Hajj "notify me" form inserts through the service role (app/api/interest/route.ts:34-38).
GRANT INSERT ON public.interests TO service_role;

COMMIT;

-- Check (last result): expect atol_verified_at and abta_verified_at = 1, service_role_can_insert_interests = true.
SELECT
  (SELECT count(*) FROM information_schema.columns
    WHERE table_schema = 'public' AND table_name = 'operator_profiles' AND column_name = 'atol_verified_at') AS atol_verified_at,
  (SELECT count(*) FROM information_schema.columns
    WHERE table_schema = 'public' AND table_name = 'operator_profiles' AND column_name = 'abta_verified_at') AS abta_verified_at,
  has_table_privilege('service_role', 'public.interests', 'INSERT') AS service_role_can_insert_interests;
```

Rollback (only if needed, and only before any code reads the columns):
`ALTER TABLE public.operator_profiles DROP COLUMN IF EXISTS atol_verified_at, DROP COLUMN IF EXISTS abta_verified_at;`

## POST-DEPLOY

Revokes. Run only after the production deployment of this release is READY and the smoke tests pass. Safe to run twice.

```sql
BEGIN;

-- 014: the API roles need nothing on operator_profiles; every read and write is Prisma on the server.
REVOKE ALL ON public.operator_profiles FROM anon, authenticated;

COMMIT;

-- Check (last result): expect 0 rows. Any row is an API-role privilege still held.
SELECT r.role, p.priv
FROM (VALUES ('anon'), ('authenticated')) AS r(role)
CROSS JOIN (VALUES ('SELECT'), ('INSERT'), ('UPDATE'), ('DELETE'), ('TRUNCATE'), ('REFERENCES'), ('TRIGGER')) AS p(priv)
WHERE has_table_privilege(r.role, 'public.operator_profiles', p.priv);
```

Rollback (restores Supabase's default API-role grants):
`GRANT ALL ON public.operator_profiles TO anon, authenticated;`
